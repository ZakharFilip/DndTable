# Пояснительная записка к проекту DnDTable

## Введение

**DnDTable** — веб-ориентированная автоматизированная информационная система виртуального стола (2D Virtual Table) для проведения настольных ролевых игр (TTRPG). Система объединяет группу участников в рамках **партии**, позволяет вестущему (GM) и игрокам совместно работать над **сценами**, размещать и редактировать **объекты** на игровом поле (токены, фигуры, текст, изображения), загружать **ассеты** и синхронизировать изменения между клиентами в **реальном времени**.

Назначение системы — сократить трудозатраты на организацию игрового стола, обеспечить единый источник данных о состоянии сцены на сервере, разграничить права участников и устранить рассогласование состояния между клиентами за счёт централизованной валидации, версионирования операций и единого механизма контроля доступа (ACL).

Архитектура проекта — **монорепозиторий** с разделением на серверную часть (REST API и WebSocket), клиентское веб-приложение и общий пакет типов и схем валидации. Разработка ведётся по функциональным **вертикалям**: авторизация → партии и пользователи → сцены и объекты → синхронизация в реальном времени → ACL → ассеты.

Документ описывает **целевую (полную) реализацию** системы в соответствии с техническим заданием, с уточнением технологических решений, подтверждённых текущей кодовой базой, где они отличаются от первоначального ТЗ и признаны более подходящими.

## 1 Аналитическая часть

### 1.1 Описание предметной области

Предметная область — организация и проведение настольных ролевых игр в цифровом формате. Классический физический стол заменяется **виртуальной сценой**: двумерное игровое поле с сеткой, на котором размещаются объекты с координатами, масштабом, поворотом и визуальными атрибутами.

**Участники и роли:**

| Роль | Назначение |
|------|------------|
| GM (ведущий) | Создание и настройка партии, сцен, управление доступом, полное или расширенное редактирование объектов и ассетов |
| Player (игрок) | Участие в партии, действия в рамках выданных прав (перемещение разрешённых токенов, просмотр видимых объектов) |

**Ключевые понятия:**

- **Партия (Party)** — долгоживущая игровая группа: участники, команды (teams), приглашения, матрица прав.
- **Сцена (Scene)** — игровое поле внутри партии; содержит иерархию **объектов сцены (SceneObject)** с компонентами данных.
- **Компонент** — фрагмент свойств объекта (Transform, Shape, Description, Visibility, Grid и др.), объединяемый по модели, близкой к **Entity–Component** (ECS): операции изменения применяются к компонентам единообразно на сервере и рассылаются клиентам.
- **Ассет (Asset)** — загруженный файл (изображение карты, токена), привязанный к партии/сцене и используемый в компоненте Shape (`kind = image`, `resourceId`).
- **Операция (Operation)** — атомарное изменение состояния (создание объекта, смена компонента, смена родителя, порядка отрисовки), передаваемое по WebSocket с идентификатором `opId` для идемпотентности.

Типовой сценарий: пользователь регистрируется → создаёт или принимает приглашение в партию → GM создаёт сцену → участники подключаются к комнате сцены → изменения объектов синхронизируются → состояние сохраняется в MongoDB, файлы ассетов — в локальном или объектном хранилище.

### 1.2 Анализ существующих аналогов

На рынке распространены облачные и самостоятельно разворачиваемые VTT-платформы. Ниже — сравнение с ориентирами и акцент на отличиях **DnDTable**.

| Критерий | Roll20 | Foundry VTT | Owlbear Rodeo | DnDTable (целевая система) |
|----------|--------|-------------|--------------|----------------------------|
| Модель развёртывания | Облако, подписка | Self-hosted, лицензия | Облако / лёгкий браузерный стол | Веб-приложение; self-hosted при развёртывании своего сервера |
| Права доступа | Роли на уровне «игрок / GM», ограниченная гранулярность | Модули, макросы; права зависят от экосистемы модулей | Минималистично: общий стол, слабая модель ролей | **Единый ACL** для REST и Socket.IO: действия `party.*`, `scene.*`, `object.*`, `asset.*`, роли GM/Player, **команды (teams)** и **оверрайды** на участника |
| Модель данных сцены | Листы, токены, карты; смешанная модель | Сцены, тайлы, акторы; мощно, но сложно для кастомизации без модулей | Простые изображения и токены на холсте | **Компонентная модель** (Transform, Shape, Description, Visibility, Grid) + ECS-операции; расширяемый реестр компонентов |
| Синхронизация | Realtime с задержками, зависимость от облака | Хост-клиент, сильная нагрузка на мастера-сессию | Быстрый P2P-стиль через хоста | **Сервер как источник истины**: валидация, ACL, идемпотентность по `opId`, оптимистичное версионирование объектов |
| Стек и прозрачность | Закрытый SaaS | Desktop + сервер модуля | Закрытый сервис | **Открытый стек** TypeScript: Express, Socket.IO, MongoDB, React; общие Zod-схемы в монорепозитории |
| UX редактора | Перегруженный интерфейс для новичков | Высокий порог входа | Очень простой, но мало возможностей | **Иерархия + инспектор + холст** (по образцу проверенного редактора стола), фокус на базовых сценариях без избыточности |

**Преимущества DnDTable перед аналогами (по замыслу системы):**

1. **Тонкая настройка разрешений** — не только бинарное «GM / не GM», а матрица действий, наследование от команд, точечные оверрайды (например, игрок команды «маг» может редактировать только объекты с определённым тегом или слоем).
2. **Единая точка проверки прав** — один `PermissionResolver` для HTTP и WebSocket; нельзя обойти ограничения, отправив операцию только через сокет.
3. **Предсказуемая синхронизация** — сервер применяет операции после валидации схем и прав; клиенты получают `opApplied` / `table:patchApplied` с согласованным состоянием; конфликты версий обрабатываются явно (HTTP 409, повторная загрузка сцены).
4. **Единый контракт данных** — пакет `@dnd-table/shared` (Zod): одни и те же типы на клиенте и сервере, меньше рассогласования форматов по сравнению с «разрозненными» API аналогов.
5. **Контролируемая сложность интерфейса** — целенаправленный набор инструментов (выбор, фигуры, текст, изображения, слои) без обязательной зависимости от магазина модулей, как в Foundry.
6. **Возможность развёртывания на собственной инфраструктуре** — данные партий, сцен и ассетов остаются под контролем оператора (MongoDB, каталог `ASSETS_DIR` или последующее подключение S3/MinIO).

### 1.3 Требования к разрабатываемой информационной системе

Требования сформированы по техническому заданию и уточнены с учётом принятых в проекте технических решений (раздел 1.5).

#### 1.3.1 Функциональные требования

**Авторизация и пользователи**

- Регистрация, вход, выход, получение текущего пользователя (`/auth/register`, `/auth/login`, `/auth/logout`, `/auth/me`).
- Защита маршрутов middleware `requireAuth` на сервере и guard маршрутов на клиенте.
- Профиль: `GET /users/me`, `PATCH /users/me`.
- Друзья: список, запрос, принятие, удаление (`/friends`, `/friends/request`, `/friends/accept`, `DELETE /friends/:userId`).

**Партии**

- CRUD партий (`/parties`).
- Участники: `/parties/:id/members` (роль GM/Player, привязка к team).
- Приглашения: `/parties/:id/invites` (по email или userId, статус, роль).
- Команды: `/parties/:id/teams` (иерархия команд при необходимости).

**Сцены и объекты**

- CRUD сцен: `/parties/:partyId/scenes`.
- Объекты: `/scenes/:sceneId/objects` — create, update, delete, move, batch.
- Компоненты (валидация через `@dnd-table/shared`):
  - **Transform** — position, rotation, scale;
  - **Shape** — rect, circle, image + `resourceId`;
  - **Description** — текстовое описание;
  - **Visibility** — `visibleTo` (команды/пользователи), `hidden`;
  - **Grid** — включение сетки, размер ячейки.
- Иерархия parent/child, порядок отрисовки `order`.

**Синхронизация в реальном времени (Socket.IO)**

- `joinParty { partyId }`, `joinScene { partyId, sceneId }`.
- `applyOperation { opId, actorId, targetId, type, payload, version, ... }` → broadcast `opApplied`.
- Дополнительно (принято в реализации): комната стола `joinTable`, пакетные патчи `table:patch` / `table:patchApplied` с оптимистичной конкуренцией по версии объекта — для высокочастотных действий (перетаскивание, resize).
- Авторизация сокета (привязка к сессии пользователя).
- Идемпотентность по `opId`; проверка ACL на сервере.

**ACL**

- Действия: `party.*`, `scene.*`, `object.*`, `asset.*`.
- Роли GM/Player, команды, оверрайды.
- UI для GM: назначение ролей и базовых прав.

**Ассеты**

- `POST /assets` (multipart), `GET /assets/:id`.
- Хранение в `ASSETS_DIR` (расширение: S3/MinIO).
- Метаданные, привязка к party/scene, ACL на чтение/загрузку.
- Использование в `Shape.kind = image` через `resourceId`.

**Справочники сущностей (нормативно-справочная информация)**

User, Party, Member, Invite, Team, Scene, SceneObject, Component, Asset, Operation, ACL/Permissions.

#### 1.3.2 Нефункциональные требования

**Заданные целевые показатели**

| Показатель | Требование |
|------------|------------|
| Удобство интерфейса | Понятный интерфейс для пользователя со средней компьютерной грамотностью; базовые сценарии доступны из UI без обращения к API |
| Время отклика | Не более **300 мс** для типовых операций (REST: чтение списка, сохранение объекта; WebSocket: применение патча/операции при нормальной нагрузке) |
| Масштабируемость | Поддержка порядка **нескольких тысяч** одновременно подключённых пользователей при горизонтальном масштабировании сервера приложений и кластера MongoDB (см. раздел 1.5) |

**Стандартные нефункциональные требования для систем класса VTT (умеренной жёсткости)**

- **Доступность** — целевой uptime 99,5% и выше при промышленном развёртывании (резервирование процесса Node, health-check `GET /health`).
- **Безопасность** — хеширование паролей (bcrypt), сессии в httpOnly-cookie, CORS по белому списку, валидация входных данных (Zod, express-validator), единый обработчик ошибок без утечки внутренних деталей.
- **Надёжность данных** — устойчивость к обрыву сети: переподключение Socket.IO, повторная синхронизация сцены; резервное копирование MongoDB (операционная процедура).
- **Сопровождаемость** — модульная структура backend (`auth`, `users`, `parties`, `scenes`, `ecs`, `realtime`, `assets`), общий пакет схем, README по модулям.
- **Совместимость** — современные браузеры (Chrome, Edge, Firefox актуальных версий); Node.js 18+; MongoDB 6.
- **Производительность клиента** — отрисовка сцены через Canvas без блокировки UI; debounce/throttle исходящих патчей при перетаскивании.
- **Расширяемость** — реестр компонент ECS, точки подключения объектного хранилища ассетов, задел `scripts-sdk` под сценарии автоматизации.

### 1.4 Анализ методов решения задачи

**Архитектурный стиль** — классическая трёхзвенная схема «клиент — сервер приложений — СУБД» с каналом реального времени.

**Методы и подходы:**

1. **REST API** — CRUD сущностей, идемпотентные запросы там, где применимо; коды HTTP для ошибок (401, 403, 404, 409).
2. **WebSocket (Socket.IO)** — комнаты по `partyId`, `sceneId`, `tableId`; push-уведомления о применённых операциях; снижение задержки по сравнению с polling.
3. **Компонентная модель (ECS-подход)** — данные объекта хранятся как набор компонентов; серверный модуль `ecs` регистрирует схемы и применяет `applyOperation` единообразно; упрощает добавление новых типов свойств без смены всей схемы документа.
4. **Оптимистичная синхронизация** — клиент применяет изменения локально, отправляет патч с `baseVersion`; сервер инкрементирует версию при совпадении; при конфликте клиент выполняет reconcile (перезагрузка объектов сцены).
5. **ACL на уровне действий** — проверка `can(userId, action, scope)` до выполнения логики; scope включает partyId, sceneId, objectId, teamId.
6. **Валидация на границе** — Zod-схемы из `@dnd-table/shared` и middleware `validate` (express-validator) для DTO.
7. **Монорепозиторий npm workspaces** — синхронное развитие API и клиента, единая версия контрактов.

**Альтернативы, отклонённые или отложенные:**

- P2P-синхронизация (как в лёгких аналогах) — отклонена: нет централизованного ACL и единого журнала состояния.
- Рендеринг через тяжёлый игровой движок — заменён на Canvas 2D (см. 1.5): достаточная производительность для 2D-стола при меньшем весе зависимостей.
- Хранение состояния сцены только в браузере — отклонено: серверная персистентность обязательна.

#### Отличия от первоначального ТЗ (принятые в проекте решения имеют приоритет)

| Аспект | В ТЗ | Принято в проекте | Обоснование |
|--------|------|-------------------|-------------|
| Аутентификация | JWT (access/refresh), `requireAuth` по токену | **Серверные сессии**: `express-session` + **connect-mongo** (httpOnly cookie) | Защита от XSS при хранении токена вне `localStorage`; проще отзыв сессии; для SPA достаточно `credentials: 'include'` |
| Хеширование паролей | Не детализировано | **bcrypt** (cost factor 10) | Отраслевой стандарт; политика сложности пароля на сервере |
| Валидация запросов | Zod | Zod + **express-validator** на маршрутах auth | Декларативные цепочки правил для HTTP-форм |
| Обработка async | — | **express-async-errors** | Централизованный `errorHandler` без обёртки каждого handler |
| Рендер сцены | PixiJS | **HTML5 Canvas 2D**, классы `CanvasRenderer`, `TableController`, `SpatialIndex` | Меньше зависимостей и размер бандла; полный контроль над отрисовкой сетки, выделения, hit-test; достаточно для 2D VTT |
| Realtime (высокочастотные правки) | `applyOperation` / `opApplied` (ECS) | Сохранены для компонентных операций **и** добавлен протокол **`table:patch`** с `opId`, `baseVersion`, событие `table:patchApplied` | Разделение «структурных» ECS-операций и «частых» геометрических патчей; оптимистичная конкуренция на уровне объекта |
| Тестирование | Методика испытаний | **Vitest** — unit-тесты изолированных модулей (геометрия, контроллер стола, история, политика пароля) | Быстрый запуск `npm test` без поднятия всего стека |
| Индексы БД | — | Скрипт `MongoFUCK/create-indexes.js` (уникальность email/username, индексы по party/scene/object) | Предсказуемая производительность выборок при росте данных |

**Масштабирование на тысячи пользователей** (архитектурный замысел): несколько инстансов Node за балансировщиком; Socket.IO с адаптером Redis для общих комнат; MongoDB replica set; статика ассетов через CDN или объектное хранилище; индексы по `partyId`, `sceneId`, `gameSessionId`, `key` объектов.

## 2 Проектная часть

### 2.1 Разработка модели базы данных

Данные хранятся в **MongoDB**. Ниже — логическая модель целевой системы (коллекции и связи). Физические имена коллекций могут соответствовать Mongoose-моделям (`users`, `parties`, `scenes`, `scene_objects`, `assets`, `operations_log` и др.).

**Сущности и атрибуты (основные поля):**

- **users** — `_id`, `email` (unique), `username` (unique), `passwordHash`, `avatar`, `createdAt`.
- **parties** — `_id`, `name`, `description`, `settings`, `ownerId`, timestamps.
- **party_members** — `partyId`, `userId`, `role` (GM|Player), `teamId?`, unique `(partyId, userId)`.
- **party_invites** — `partyId`, `email|userId`, `status`, `role`, `invitedBy`, timestamps.
- **teams** — `_id`, `partyId`, `name`, `parentTeamId?` (иерархия).
- **scenes** — `_id`, `partyId`, `name`, `order`, `settings` (в т.ч. Grid по умолчанию).
- **scene_objects** — `_id`, `sceneId`, `parentId?`, `order`, `components` (вложенный объект или отдельные поля по типам компонентов), `version` (для конкуренции).
- **assets** — `_id`, `partyId`, `sceneId?`, `filename`, `mimeType`, `size`, `storageKey`, `uploadedBy`, timestamps.
- **acl_rules** — `partyId`, `subject` (role|team|user), `action`, `allow|deny`, `resourceScope`.
- **sessions** (express-session) — `sid`, `userId`, `expires` (коллекция `sessions` в MongoDB).

**Диаграмма «сущность–связь» (текстовое описание; в дальнейшем — графическая ER-диаграмма)**

```
[User] 1──* [PartyMember] *──1 [Party]
[Party] 1──* [Team]
[Party] 1──* [PartyInvite]
[Party] 1──* [Scene]
[Scene] 1──* [SceneObject] (parentId → SceneObject, иерархия)
[Party] 1──* [Asset]
[Scene] 0──* [Asset] (опциональная привязка)
[Party] 1──* [AclRule]
[User] — авторизация → [Session store]
```

*Пометка для оформления: построить ER-диаграмму в нотации Crow’s Foot по описанию выше.*

**Индексы (план):**

- `users`: unique `email`, unique `username`.
- `party_members`: unique `(partyId, userId)`; index `userId`.
- `scenes`: index `partyId`.
- `scene_objects`: index `sceneId`; index `(sceneId, parentId)`; unique `(sceneId, clientKey)` при использовании стабильного клиентского ключа.
- `assets`: index `partyId`.
- Для протокола патчей стола (промежуточный и целевой контур сцены): `(sceneId, key)` unique, index `sceneId`.

### 2.2 Проектирование программного обеспечения / информационной системы

**Логическая архитектура (текстовая диаграмма; в дальнейшее — диаграмма компонентов UML)**

```
┌─────────────────────────────────────────────────────────────┐
│                     Browser (React SPA)                      │
│  Pages: Login, Dashboard, Party, SceneEditor                 │
│  api/* (REST)  realtime/socket  tabletop/* (Canvas, Sync)  │
└───────────────────────────┬─────────────────────────────────┘
                            │ HTTP + WebSocket (credentials)
┌───────────────────────────▼─────────────────────────────────┐
│              Express Application (Node.js)                   │
│  auth │ users │ parties(+acl) │ scenes │ ecs │ assets        │
│  realtime/gateway │ shared(middleware, errors, health)       │
└───────────────────────────┬─────────────────────────────────┘
                            │
┌───────────────────────────▼─────────────────────────────────┐
│  MongoDB (данные)     │  ASSETS_DIR / S3 (файлы)           │
└─────────────────────────────────────────────────────────────┘

        @dnd-table/shared (Zod schemas, patch types, ECS types)
```

**Модули backend (целевая ответственность):**

| Модуль | Ответственность |
|--------|-----------------|
| `auth` | Регистрация, вход, выход, сессия, политика пароля |
| `users` | Профиль, друзья |
| `parties` | CRUD партий, участники, инвайты, teams |
| `parties/acl` | PermissionResolver, middleware `requirePermission` |
| `scenes` | CRUD сцен и объектов, загрузка полного состояния сцены |
| `ecs` | ComponentRegistry, `applyOperation` |
| `realtime` | Socket.IO: joinParty, joinScene, applyOperation, joinTable, table:patch |
| `assets` | Multipart upload, выдача файлов, ACL |
| `storage` | Подключение Mongo, репозитории (целевое выделение доступа к БД) |

**Модули frontend:**

| Каталог | Ответственность |
|---------|----------------|
| `app/` | Shell, роутинг, RouteGuards |
| `pages/` | Login, Register, Dashboard, Party, редактор сцены (SessionTablePage / SceneEditor) |
| `api/` | HTTP-клиент с cookie |
| `realtime/` | Socket.IO клиент |
| `tabletop/` | Модель объектов, геометрия, рендер, контроллер, TableSync, HistoryManager |
| `party/` | Hierarchy, Inspector, Assets (целевые панели партии) |
| `state/` | Сессия пользователя, состояние сцены |

**Поток данных при редактировании объекта (реальное время):**

1. Пользователь перемещает объект на Canvas → `TableController` обновляет локальное состояние.
2. `TableSync.enqueue` формирует `TablePatchOp` с `baseVersion`.
3. Socket `table:patch` → сервер `applyTablePatches` → MongoDB → broadcast `table:patchApplied`.
4. Другие клиенты применяют `AppliedOp` к локальному списку объектов.
5. При 409 — `onConflict`: повторный `GET` полного состояния сцены.

*Пометка для оформления: диаграмма последовательности (UML Sequence) для шагов 1–5.*

**Пакет `@dnd-table/shared`:**

- Схемы компонентов ECS (Transform, Shape, Description, Visibility, Grid).
- Типы `SceneObject`, payload Socket.IO join.
- Типы tabletop и **TablePatchOp** / **AppliedOp** — единый wire-format для REST и WebSocket.

## 3 Реализация и тестирование программного обеспечения

Раздел описывает **целевую полную реализацию**; фактическое состояние репозитория на момент подготовки записки содержит реализованные вертикали (авторизация на сессиях, редактор стола с Canvas, протокол патчей, Socket.IO, unit-тесты) и модули в стадии подключения (parties, scenes, ecs, assets, friends — заглушки или частичная логика). Ниже — состав и методика в терминах готовой системы.

### 3.1 Реализация основных функций программного обеспечения

#### 3.1.1 Авторизация

- Регистрация с проверкой уникальности email и username, политикой пароля (заглавная, строчная, цифра, минимум 8 символов).
- Вход: установка `userId` в серверной сессии, cookie `httpOnly`, `sameSite=lax`.
- `GET /auth/me` — текущий пользователь; `POST /auth/logout` — уничтожение сессии.
- Middleware `requireAuth` для REST; для Socket.IO — проверка сессии/handshake (целевое требование ТЗ).

#### 3.1.2 Пользователи и друзья

- CRUD профиля, аватар.
- Социальный граф: запрос/принятие/удаление друзей для приглашений в партию.

#### 3.1.3 Партии

- Создание партии, список «мои партии», приглашения по email/userId, управление участниками и командами.
- Роли GM/Player при входе в партию.

#### 3.1.4 Сцены и объекты

- CRUD сцен в контексте партии.
- Объекты с компонентами из `@dnd-table/shared`; иерархия parent/child.
- REST: пакетное сохранение, полная загрузка `.../full` для инициализации редактора.
- Клиент: `CanvasRenderer` отрисовывает rect/ellipse/text/image/token; `SpatialIndex` ускоряет hit-test; `InspectorPanel` редактирует свойства выбранного объекта.

#### 3.1.5 ECS и операции

- `ComponentRegistry` регистрирует Transform, Shape, Description, Visibility, Grid.
- `applyOperation` на сервере: set/remove component, reorder, parent/child.
- Идемпотентность: хранение обработанных `opId` (коллекция или TTL-кэш).

#### 3.1.6 Realtime

- Комнаты Socket.IO: `party:{id}`, `scene:{partyId}:{sceneId}`, `table:{sceneId}`.
- События ECS: `applyOperation` → `opApplied`.
- События патчей: `table:patch` (ack с результатом) → `table:patchApplied` (broadcast).
- Клиент `TableSync`: очередь, debounce/throttle, обработка конфликтов.

#### 3.1.7 ACL

- `PermissionResolver.can(userId, action, scope)`.
- Middleware на маршрутах и в обработчиках сокета до применения операции.
- UI GM для назначения прав команде/игроку.

#### 3.1.8 Assets

- Загрузка multipart, сохранение в `ASSETS_DIR`, метаданные в MongoDB.
- Выдача `GET /assets/:id` с проверкой ACL.
- Привязка `resourceId` в Shape; кэш изображений на клиенте в `CanvasRenderer`.

#### 3.1.9 Инфраструктура и конфигурация

- Переменные окружения: `MONGODB_URI`, `SOCKET_CORS_ORIGIN`, `ASSETS_DIR`, `SESSION_SECRET`, `PORT`.
- Health-check: `GET /health` → `{ ok: true, ... }`.
- Docker для MongoDB 6; скрипт создания индексов.
- Скрипты npm: `dev:backend`, `dev:frontend`, `build`, `test`.

### 3.2 Тестирование программного обеспечения

Тестирование сочетает **ручные** и **автоматизированные** методы.

#### 3.2.1 Ручное тестирование

| Метод | Объект проверки |
|-------|-----------------|
| Сквозные сценарии (E2E вручную) | Регистрация → создание партии → сцена → два браузера → синхронное перемещение объекта |
| Функциональное | Каждая вертикаль ТЗ: auth, parties, scenes, realtime, ACL, assets |
| Негативное | Неверный пароль, доступ без сессии, операция без права, конфликт версий (два клиента правят один объект) |
| UI/UX | Читаемость панелей, работа горячих клавиш, масштаб/панорама холста |
| Кросс-браузерное | Chrome, Edge, Firefox — вход, редактор, сокет |
| Нагрузочное (выборочно) | Множество патчей при перетаскивании; задержка &lt; 300 мс в локальной сети |

#### 3.2.2 Автоматизированное тестирование

Запуск из корня репозитория:

```bash
npm test
```

Используется **Vitest** (`tests/vitest.config.ts`). Тесты изолированы от поднятия MongoDB и HTTP-сервера — проверяют детерминированную логику:

| Файл | Что проверяется |
|------|-----------------|
| `geometry.test.ts` | AABB объектов, попадание в прямоугольник выделения, преобразования screen↔world |
| `TableController.test.ts` | Ограничение zoom, инварианты перетаскивания |
| `HistoryManager.test.ts` | undo/redo, сброс redo после новой операции |
| `authPasswordPolicy.test.ts` | Политика сложности пароля `AuthService._isPasswordStrong` |

**Планируемое расширение автотестов (целевая система):**

- Интеграционные тесты API (supertest): auth, parties, scenes с тестовой БД.
- Тесты `applyTablePatches` / `applyOperation` на конфликты версий и идемпотентность `opId`.
- Тесты ACL: матрица allow/deny для ролей и teams.

#### 3.2.3 Приёмочные критерии

Приёмка по вертикалям — в соответствии с техническим заданием:

1. **Auth** — регистрация и вход; защищённые запросы без сессии отклоняются; выход завершает сессию.
2. **Users/Friends** — профиль редактируется; цикл запрос/принятие/удаление друга работает.
3. **Parties** — создание партии, инвайт, принятие; участники и teams сохраняются.
4. **Scenes/Objects** — CRUD сцен и объектов; валидация Zod; объект отображается и редактируется на холсте.
5. **Realtime** — два клиента на одной сцене видят согласованные изменения с задержкой не выше целевого NFR.
6. **ACL** — запрещённые действия возвращают 403; UI GM меняет базовые права.
7. **Assets** — файл загружается и отображается в объекте с `Shape.kind = image`.

**Общий критерий готовности системы:** прохождение перечисленных сценариев при ручной приёмке **и** успешный прогон `npm test` без падений; health-check сервера доступен после развёртывания.

## Заключение

В рамках проекта **DnDTable** спроектирована и реализуется веб-система виртуального стола для настольных ролевых игр, ориентированная на совместную работу участников партии над сценами с разграничением прав и синхронизацией в реальном времени. Проведён анализ предметной области и коммерческих аналогов (Roll20, Foundry VTT, Owlbear Rodeo); показано, что ключевое конкурентное преимущество разрабатываемой системы — **гибкая модель ACL**, единая проверка прав для REST и WebSocket, компонентная модель данных и сервер-centric синхронизация с идемпотентными операциями и версионированием объектов.

Спроектирована модель данных на основе MongoDB, модульная архитектура монорепозитория и интерфейс редактора сцены с панелями иерархии, инспектора и Canvas-холста. От первоначального технического задания приняты уточнённые технологические решения: **серверные сессии** вместо хранения JWT в клиенте, **Canvas 2D** вместо PixiJS, протокол **патчей с оптимистичной конкуренцией** наряду с ECS-операциями, стек **bcrypt / express-validator / Vitest**.

Реализованы (и развиваются) подсистемы аутентификации, интерактивного редактора стола, синхронизации через Socket.IO, общих схем в `@dnd-table/shared`, автоматизированные unit-тесты критичной клиентской и серверной логики. В плане завершения оставшихся модулей — партии, полноценные сцены в терминах домена Party/Scene, ACL, ассеты и интеграционное тестирование API.

Результатом работы является целостная информационная система, пригодная для развёртывания на собственой инфраструктуре, с понятным интерфейсом, заданными нефункциональными характеристиками (отклик до 300 мс, масштабирование до тысяч одновременных пользователей при кластерной конфигурации) и документированными критериями приёмки по функциональным вертикалям и автоматизированным тестам.
