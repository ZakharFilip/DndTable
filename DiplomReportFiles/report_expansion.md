
#### Обзор литературных источников по теме

В учебной и научной литературе вопросы проектирования информационных систем рассматриваются через призму жизненного цикла программного обеспечения. Для распределённых приложений с интерактивным UI актуальны модели клиент-серверного взаимодействия и обмена событиями в реальном времени. Методики объектно-ориентированного анализа (UML, RUP) применимы к декомпозиции VTT на подсистемы: учёт пользователей, управление партией, редактор сцены, синхронизация.

Публикации по качеству ПО (ISO/IEC 25010) задают рамки нефункциональных требований: производительность, надёжность, удобство использования. Документация промышленных технологий (Node.js, MongoDB, React, Socket.IO) используется как нормативно-техническая база при обосновании стека.

#### Детализация сущностей предметной области

Компонент **Transform** хранит вектор положения (x, y), опционально z-порядок, масштаб и угол поворота. **Shape** определяет тип геометрии (`rect`, `circle`) или ссылку на растровое изображение через `resourceId`. **Description** содержит текстовое поле для заметок ведущего или игроков. **Visibility** реализует fog-of-war и выборочную видимость: массив `visibleTo` может содержать идентификаторы пользователей или команд; флаг `hidden` скрывает объект от неавторизованных ролей. **Grid** задаёт шаг сетки для привязки перемещений.

Иерархия `parentId` позволяет группировать объекты (например, рамка карты и токены на ней). Поле `order` управляет z-order при отрисовке на Canvas.

#### 1.2.1 Roll20 (дополнительный анализ)

Платформа ориентирована на широкую аудиторию D&D и смежных систем. Экономическая модель подписки влияет на доступность продвинутых функций (динамическое освещение, API). С точки зрения проектирования ACL Roll20 не предоставляет декларативной матрицы действий на уровне отдельного объекта сцены — ограничения задаются преимущественно ролью листа и слоём карты. Для DnDTable это является мотивацией внедрения `PermissionResolver` с явными действиями.

#### 1.2.2 Foundry VTT (дополнительный анализ)

Foundry демонстрирует высокую гибкость за счёт модулей сообщества. Однако воспроизводимость конфигурации прав в разных инсталляциях низкая: набор модулей не стандартизирован. DnDTable проектируется с фиксированным ядром ACL в коде сервера, что упрощает тестирование и аудит безопасности.

#### 1.2.3 Owlbear Rodeo (дополнительный анализ)

Минимализм Owlbear снижает время входа в сессию, но переносит ответственность за долговременное хранение кампаний на внешние инструменты. DnDTable сохраняет партии и сцены в MongoDB, обеспечивая непрерывность кампаний.

#### 1.3.1 Детализация функциональных требований

Критический контур функциональности включает авторизацию, CRUD объектов стола, базовую синхронизацию и отображение на Canvas. Следующий уровень охватывает партии, инвайты и друзей. Расширенный уровень — ACL с оверрайдами, ассеты и иерархию teams.

Каждый REST-метод возвращает структурированные ошибки (`success`, `error`, `message`) через единый `errorHandler`. Socket-события при отказе в правах не применяют изменение и возвращают ack с кодом ошибки.

#### 1.3.2 Расчётные соображения по производительности

Требование 300 мс для типовой операции интерпретируется как 95-й перцентиль задержки на стенде: сервер Node на localhost, MongoDB без сетевой задержки, payload патча до 10 операций. При перетаскивании объекта клиент генерирует серию патчей; debounce 300 мс в `TableSync` агрегирует их в один запрос, снижая нагрузку на БД.

Масштаб «несколько тысяч пользователей» достигается на кластере с sticky sessions или Redis adapter для Socket.IO. Горизонтальное масштабирование MongoDB — sharding по `partyId` при росте объёма документов `scene_objects`.

#### 1.4.1 Сравнение методологий проектирования

Структурный подход (IDEF0, DFD) применим к описанию потоков данных между партией и сценой. Объектно-ориентированный подход (UML) — к классам `TableController`, `GameSessionsService`, моделям Mongoose. Для проекта выбран ОО-подход как соответствующий стеку TypeScript и модульной структуре репозитория.

#### 1.5.1 Обоснование MongoDB

Реляционная СУБД обеспечила бы жёсткие JOIN для иерархии объектов, но усложнила бы эволюцию схемы компонентов. Документная модель MongoDB позволяет хранить `components` как вложенный объект и индексировать по `sceneId` и `key`. Транзакции multi-document доступны при необходимости атомарного batch-update.

#### 1.5.2 Обоснование TypeScript и монорепозитория

Статическая типизация снижает класс ошибок при передаче `TablePatchOp` между клиентом и сервером. Workspaces объединяют `backend`, `frontend`, `packages/shared` в одной версии контракта.

### 2.1.1 Физическая организация коллекций

Коллекция `scene_objects` может достигать большого объёма на активной сцене (тысячи токенов). Рекомендуется проекция полей при выборке для списка (без тяжёлых `props`) и полная загрузка по endpoint `.../full` при открытии редактора.

Коллекция `sessions` для express-session изолирована; TTL-индекс на `expires` предотвращает неограниченный рост.

### 2.2.1 Детализация вариантов использования UC-03

**Предусловия:** пользователь аутентифицирован, состоит в партии, имеет право `object.update` на объект или класс объектов.

**Основной поток:** (1) открыть сцену или игровую сессию; (2) выбрать инструмент; (3) создать или выделить объект; (4) изменить свойства в инспекторе; (5) клиент формирует патч; (6) сервер применяет и рассылает; (7) остальные клиенты обновляют Canvas.

**Альтернативный поток А1 (конфликт версий):** на шаге 6 сервер возвращает 409; клиент загружает полное состояние и повторяет операцию пользователя при необходимости.

### 2.2.2 Модель развёртывания

Узлы: «Браузер пользователя», «Сервер приложений Node», «MongoDB», «Файловое хранилище ASSETS_DIR». Протоколы: HTTPS, WSS. В промышленной конфигурации добавляются балансировщик и Redis. Подробное описание — в приложении Б.

### 2.3.1 Сценарии интерфейса для роли Player

Игрок видит ограниченный набор инструментов: перемещение разрешённых токенов, просмотр описаний, без доступа к ACL и удалению чужих объектов. Скрытые объекты (`Visibility.hidden` или `visibleTo` без id игрока) не отрисовываются.

### 2.3.2 Сценарии интерфейса для роли GM

Ведущий имеет полный доступ к иерархии, загрузке ассетов, настройке сетки, управлению слоями. Панель ACL доступна из контекста партии.

#### 3.1.1 Детализация реализации AuthService

Метод `register` выполняет нормализацию email (lowercase, trim), проверку коллизий, валидацию пароля `_isPasswordStrong`, хеширование bcrypt. Ответ содержит объект `user` без `passwordHash`. Метод `login` сравнивает хеш; при успехе устанавливается `req.session.userId`.

Маршрутизатор использует `express-validator` для синтаксических проверок и `validate` middleware перед вызовом сервиса. Ошибки домена — через `HttpError` с кодами `EMAIL_ALREADY_EXISTS`, `VALIDATION_ERROR`.

#### 3.1.4 Детализация CanvasRenderer и TableController

`CanvasRenderer` рисует сетку, объекты по слоям, рамку выделения, handles изменения размера. `TableController` обрабатывает pointer events: pan, zoom (с ограничением min/max scale), drag, resize, rotate. `pickHandle` определяет активный маркер трансформации.

`geometry.ts` реализует преобразования координат screen↔world, AABB для hit-test повёрнутых прямоугольников, попадание в область выделения.

#### 3.1.6 Детализация applyTablePatches

Алгоритм последовательно обрабатывает массив `ops`. Для `create` — вставка с `version=1`; уникальный индекс `(gameSessionId, key)` предотвращает дубликаты. Для `update` — атомарный `findOneAndUpdate` с условием по `version`; при неуспехе — запись в `conflicts`. Для `delete` — `deleteOne` с проверкой версии.

REST-дублирование: `POST /api/sessions/:id/patch` применяет те же функции и инициирует broadcast через `getIoInstance()`.
