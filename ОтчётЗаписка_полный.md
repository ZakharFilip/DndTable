## ВВЕДЕНИЕ

Современный этап развития общества характеризуется высокой степенью информатизации социальных и досуговых практик. Средства информационных технологий проникают в сферы, где ещё недавно доминировали исключительно офлайн-форматы взаимодействия. К таким сферам относится и организация настольных ролевых игр (TTRPG): группы игроков всё чаще используют сетевые сервисы для совместного ведения партий, отображения карт, перемещения фигур и обмена игровыми материалами.

Виртуальный стол (Virtual Tabletop, VTT) представляет собой программный комплекс, имитирующий игровое поле, объекты на нём и правила взаимодействия участников. Качество VTT определяется не только скоростью отрисовки, но и согласованностью данных между клиентами, возможностью разграничения прав, удобством подготовки сцен и надёжностью хранения пользовательских материалов. Коммерческие и открытые решения на рынке демонстрируют различные компромиссы между простотой, функциональностью и стоимостью владения.

Актуальность разработки веб-системы DnDTable обусловлена следующими факторами. Во-первых, распространённые облачные платформы ограничивают гибкость настройки прав доступа и хранение данных на стороне пользователя. Во-вторых, самостоятельно разворачиваемые решения нередко требуют сложной инсталляции и экосистемы модулей, что повышает порог входа для ведущего игры. В-третьих, целесообразно иметь прозрачный стек TypeScript с единым контрактом данных между клиентом и сервером, что упрощает сопровождение и развитие системы.

Это послужило основанием для выбора темы выпускной квалификационной работы: разработка веб-ориентированной автоматизированной информационной системы **DnDTable** — виртуального двумерного стола для проведения настольных ролевых игр с поддержкой партий, сцен, компонентной модели объектов, синхронизации в реальном времени и разграничения доступа.

**Цель работы** — разработать информационную систему DnDTable, обеспечивающую совместную работу ведущего и игроков над игровыми сценами, централизованное хранение состояния, контроль прав и обмен изменениями в режиме реального времени.

Для достижения указанной цели поставлены следующие **задачи**:

1. Изучить предметную область настольных ролевых игр и требования к виртуальным столам.
2. Проанализировать существующие аналоги и обосновать необходимость разработки собственной системы.
3. Сформировать функциональные и нефункциональные требования к DnDTable.
4. Разработать информационную модель данных и архитектуру программного обеспечения.
5. Спроектировать пользовательские интерфейсы ключевых сценариев (авторизация, партия, редактор сцены).
6. Реализовать программные модули серверной и клиентской частей, общий пакет схем валидации.
7. Реализовать механизмы синхронизации состояния сцены и контроля доступа.
8. Провести тестирование системы и оценить соответствие требованиям.

**Объект исследования** — процессы организации и проведения совместных игровых сессий в цифровой среде.

**Предмет исследования** — методы и средства проектирования веб-ориентированной информационной системы виртуального стола.

## 1 Аналитическая часть

### 1.1 Описание предметной области


Предметная область выпускной квалификационной работы — организация и проведение настольных ролевых игр с использованием информационных технологий. Традиционная игра предполагает физическое игровое поле, миниатюры, карты и совместное присутствие участников. При удалённом взаимодействии возникает потребность в цифровом аналоге стола, сохраняющем пространственную модель сцены и правила видимости объектов.

В рамках DnDTable выделяются роли **ведущего (GM)** и **игрока (Player)**. Ведущий формирует партию, создаёт сцены, управляет объектами и назначает права. Игрок взаимодействует с разрешёнными объектами: перемещение токена, просмотр описаний. Дополнительно вводится понятие **команды (team)** — группы игроков внутри партии, для которых могут наследоваться права.

Центральной сущностью предметной области является **партия (Party)** — устойчивая группа пользователей с общим набором сцен и настроек доступа. **Сцена (Scene)** — экземпляр игрового поля внутри партии. На сцене размещаются **объекты (SceneObject)**, каждый из которых описывается набором **компонентов**: Transform (координаты, масштаб, поворот), Shape (геометрия или изображение), Description (текст), Visibility (кому виден объект), Grid (параметры сетки).

Операции изменения состояния передаются на сервер и применяются после проверки схемы данных и прав. Для высокочастотных действий (перетаскивание) используется протокол **патчей** с полем `baseVersion`, что снижает нагрузку по сравнению с полной пересылкой документа объекта.

Типовой бизнес-процесс: регистрация пользователя → создание или вступление в партию → создание сцены ведущим → подключение участников к комнате realtime → редактирование объектов → сохранение в MongoDB и рассылка событий подписчикам. Детальное текстовое описание диаграмм приведено в приложении Б.

Проблемы, решаемые системой: рассогласование состояния у клиентов при обмене файлами; отсутствие единого журнала изменений; сложность тонкой настройки прав в ряде коммерческих VTT; зависимость от проприетарных облаков. Результатом анализа предметной области является постановка задачи разработки веб-системы с сервером как источником истины и единым ACL.

### 1.2 Анализ существующих аналогов

Для обоснования проектных решений рассмотрены распространённые VTT-платформы. Критерии сравнения: модель развёртывания, гранулярность прав, структура данных сцены, механизм синхронизации, открытость стека, сложность интерфейса.

**Roll20** — облачный сервис с подписной моделью. Сильные стороны: интеграция с листами персонажей, библиотека ассетов, устоявшееся сообщество. Ограничения: права задаются преимущественно на уровне «игрок / GM»; зависимость от доступности облака; закрытый исходный код, что затрудняет адаптацию под специфические правила домашней кампании.

**Foundry VTT** — настольное приложение с локальным хостом сессии. Обеспечивает богатую экосистему модулей, детальную настройку сцен и освещения. Недостатки: высокий порог входа; распределение нагрузки на машину ведущего; права и поведение сильно зависят от сторонних модулей, что осложняет формальную верификацию политики доступа.

**Owlbear Rodeo** — минималистичный браузерный стол с акцентом на скорость старта. Подходит для быстрых сессий, однако не предоставляет развитой модели партий, команд и матрицы ACL; синхронизация опирается на модель «комнаты хоста».

Необходимость собственной разработки обосновывается сочетанием требований: единый `PermissionResolver` для REST и WebSocket; компонентная модель с расширяемым реестром; прозрачный монорепозиторий; возможность развёртывания на инфраструктуре заказчика без лицензионных ограничений Foundry.

Конкурентные преимущества DnDTable:

1. Тонкая настройка разрешений на уровне действий `party.*`, `scene.*`, `object.*`, `asset.*`.
2. Единая точка проверки прав — исключение обхода через канал сокета.
3. Предсказуемая синхронизация с идемпотентностью по `opId` и обработкой конфликтов версий (HTTP 409).
4. Общий пакет `@dnd-table/shared` (Zod) для клиента и сервера.
5. Редактор «иерархия — холст — инспектор» без обязательного магазина модулей.

### 1.3 Требования к разрабатываемой информационной системе

Требования сформированы в ходе анализа предметной области, сравнения аналогов и этапа проектирования информационной системы DnDTable.

#### 1.3.1 Функциональные требования

Система должна обеспечивать следующие области функциональности, каждая из которых имеет критерии приёмки.

**Авторизация.** Регистрация (`POST /auth/register`), вход (`POST /auth/login`), выход (`POST /auth/logout`), получение текущего пользователя (`GET /auth/me`). Защита REST-маршрутов middleware `requireAuth` и guard на клиенте. В реализации приняты серверные сессии `express-session` с хранением в MongoDB (connect-mongo), cookie `httpOnly`.

**Пользователи и друзья.** Профиль: `GET /users/me`, `PATCH /users/me`. Социальный граф: запрос, принятие и удаление друзей для упрощения приглашений в партию.

**Партии.** CRUD `/parties`; участники `/parties/:id/members` с ролями GM/Player и привязкой к team; приглашения `/parties/:id/invites`; команды `/parties/:id/teams` с опциональной иерархией.

**Сцены и объекты.** CRUD `/parties/:partyId/scenes`; операции над `/scenes/:sceneId/objects` (создание, обновление, удаление, перемещение, пакетные операции). Компоненты Transform, Shape, Description, Visibility, Grid валидируются схемами Zod. Поддерживаются parent/child и порядок `order`. Эксплуатационная реализация совместного редактирования стола в текущей версии системы обеспечивается модулем игровых сессий (`/api/sessions`) с коллекцией `table_objects`.

**Realtime.** Socket.IO: `joinParty`, `joinScene`, `applyOperation` → `opApplied`; дополнительно `joinTable`, `table:patch` → `table:patchApplied` для частых геометрических изменений. Требуется привязка сокета к сессии пользователя, идемпотентность `opId`, проверка ACL до применения.

**ACL.** Действия в доменах party, scene, object, asset; роли, команды, оверрайды; UI для GM.

**Ассеты.** `POST /assets`, `GET /assets/:id`; хранение в `ASSETS_DIR`; использование в Shape (`kind = image`, `resourceId`).

Нормативно-справочная информация включает сущности User, Party, Member, Invite, Team, Scene, SceneObject, Component, Asset, Operation, ACL/Permissions, GameSession.

#### 1.3.2 Нефункциональные требования

Целевые показатели проекта:

| Показатель | Требование |
|------------|------------|
| Удобство интерфейса | Понятный UI для пользователя со средней компьютерной грамотностью |
| Время отклика | Не более 300 мс для типовых REST- и socket-операций при штатной нагрузке |
| Масштабируемость | Порядка нескольких тысяч одновременных подключений при кластерном развёртывании |

Дополнительно в соответствии с ГОСТ Р ИСО/МЭК 25010 зафиксированы:

- **Надёжность** — переподключение Socket.IO, повторная загрузка сцены при конфликте версий; резервное копирование MongoDB.
- **Безопасность** — bcrypt для паролей; CORS по белому списку; валидация входа; единый обработчик ошибок.

### 1.4 Анализ методов решения задачи

Задача создания VTT относится к классу информационных систем совместной работы (groupware) с элементами CAD-подобного редактора 2D-сцены. Применяется трёхзвенная архитектура: браузер (React SPA), сервер приложений (Node.js), СУБД (MongoDB) и файловое хранилище ассетов.

**REST** используется для CRUD и загрузки полного состояния сцены. Преимущества: кэшируемость GET-запросов, стандартные коды ответов, простота отладки.

**WebSocket (Socket.IO)** обеспечивает push-доставку событий в комнаты `party`, `scene`, `table`. По сравнению с long polling снижается задержка и нагрузка на установку соединений.

**Компонентная модель (ECS)** декомпозирует свойства объекта; серверный модуль `ecs` применяет операции `applyOperation` единообразно, что упрощает расширение типов компонентов без миграции всей коллекции под фиксированную схему.

**Оптимистичная синхронизация** предполагает локальное применение изменений и отправку патча с `baseVersion`. Сервер инкрементирует версию при совпадении; иначе возвращается конфликт и клиент выполняет reconcile — повторный `GET` полного состояния.

**ACL** реализуется как функция `can(userId, action, scope)` с вызовом до бизнес-логики в REST и обработчиках сокета.

Отклонённые альтернативы: P2P-синхронизация (нет централизованного ACL); хранение сцены только в localStorage; использование тяжёлого игрового движка PixiJS при достаточности Canvas 2D для задачи.

## 2 Проектная часть

### 2.1 Разработка модели базы данных

Логическая модель построена для MongoDB. Коллекции и ключевые поля:

- **users** — учётные записи (`email`, `username` уникальны, `passwordHash`, `avatar`).
- **parties** — партии (`name`, `description`, `ownerId`, `settings`).
- **party_members** — связь пользователь–партия (`role`, `teamId`), уникальный индекс `(partyId, userId)`.
- **party_invites** — приглашения (`email` или `userId`, `status`, `role`).
- **teams** — команды (`partyId`, `parentTeamId` для иерархии).
- **scenes** — сцены (`partyId`, `name`, `order`, `settings`).
- **scene_objects** — объекты (`sceneId`, `parentId`, `order`, `components`, `version`, стабильный `key`).
- **game_sessions** — игровые сессии стола (`name`, `createdBy`, `isPrivate`, метаданные).
- **table_objects** — объекты в рамках сессии (`gameSessionId`, `key`, `version`, `components`, геометрия).
- **assets** — метаданные файлов (`partyId`, `sceneId?`, `storageKey`, `mimeType`).
- **acl_rules** — правила (`subject`, `action`, `allow|deny`, `resourceScope`).
- **sessions** — хранилище express-session.

Связи: User 1—* PartyMember *—1 Party; Party 1—* Scene; Scene 1—* SceneObject (рекурсия parentId); Party 1—* Asset; GameSession 1—* TableObject.

Текстовое описание ER-модели и кардинальностей приведено в приложении Б.

Компоненты объекта могут храниться вложенным документом `components` либо денормализованными полями — выбор зависит от частоты запросов по типу компонента. Для протокола патчей используется поле `version` на каждом объекте.

Индексы: уникальность `users.email`, `users.username`; `party_members (partyId, userId)`; `scenes.partyId`; `scene_objects (sceneId, key)` unique; `table_objects (gameSessionId, key)` unique; `assets.partyId`.

### 2.2 Проектирование программного обеспечения информационной системы

Архитектура — **клиент-сервер** с каналом реального времени. Состав компонентов описан в приложении Б.

Монорепозиторий npm workspaces: `backend`, `frontend`, `packages/shared`, `packages/scripts-sdk`.

**Варианты использования:**

1. **UC-01 Регистрация и вход** — актор: гость; создание учётной записи, установка сессии.
2. **UC-02 Управление партией** — актор: GM; CRUD партии, инвайты, участники, teams.
3. **UC-03 Редактирование сцены** — актор: GM/Player; CRUD объектов в пределах ACL.
4. **UC-04 Синхронизация в реальном времени** — акторы: все участники сцены; joinScene, патчи, broadcast.
5. **UC-05 Управление правами** — актор: GM; настройка ACL.
6. **UC-06 Работа с ассетами** — загрузка и привязка к Shape.

**Поток синхронизации (текстовое описание):**

1. Клиент A: `TableController` изменяет координаты → `TableSync.enqueue(patch)`.
2. Socket `table:patch` → сервер `applyTablePatches`.
3. MongoDB: `findOneAndUpdate` с условием `version == baseVersion`.
4. Broadcast `table:patchApplied` в комнату `table:{sessionId}`.
5. Клиент B применяет `AppliedOp` к локальному состоянию.

Модули backend: `auth`, `users`, `parties`, `parties/acl`, `scenes`, `ecs`, `gamesessions`, `realtime`, `assets`, `shared`. Модули frontend: `app`, `pages`, `api`, `realtime`, `tabletop`, `party`, `state`.

Пакет `@dnd-table/shared` содержит Zod-схемы компонентов, типы `TablePatchOp` / `AppliedOp`, payload для join.

### 2.3 Проектирование интерфейсов

SPA на React Router. Маршруты: `/login`, `/register`, `/dashboard`, `/party/:id`, `/party/:partyId/scene/:sceneId`, `/session/:sessionId` (редактор игровой сессии), `/profile`.

Редактор сцены реализует паттерн, близкий к IDE: дерево объектов слева, центральный Canvas, инспектор свойств справа, панель инструментов (select, rect, ellipse, text, image, слои). Статус синхронизации отображает состояния `idle`, `syncing`, `ok`, `conflict`, `error`.

Для GM предусмотрен экран настройки ACL в контексте партии. Визуальный стиль — TailwindCSS: единые отступы, контрастные состояния кнопок, доступность с клавиатуры (undo/redo, удаление) через `HistoryManager` с последующей отправкой патчей на сервер.

## 3 Реализация и тестирование программного обеспечения

### 3.1 Реализация основных функций программного обеспечения

Система развёртывается как монорепозиторий. Сервер слушает порт 4000 (по умолчанию), клиент Vite — 5173. MongoDB 6 — в Docker или локально. На сервере приложений смонтированы маршруты `/auth` и `/api/sessions`; шлюз Socket.IO обслуживает события `table:patch` и смежные.

#### 3.1.1 Модуль авторизации

`AuthService` выполняет регистрацию с проверкой уникальности email и username, политикой пароля (заглавная, строчная, цифра, длина ≥ 8). Пароль хешируется bcrypt (10 раундов). При успешном входе в сессию записывается `userId`; cookie `httpOnly`, `sameSite=lax`. Маршруты защищены `requireAuth`, извлекающим `userId` из `req.session`.

#### 3.1.2 Модуль игровых сессий (gamesessions)

Модуль `gamesessions` реализует эксплуатационный контур совместного стола. `GameSessionsService.createSession` создаёт документ `GameSession`; `getFull` возвращает объекты `table_objects` и состояние viewport для инициализации редактора. `applyPatch` применяет массив `TablePatchOp` с оптимистичной блокировкой по `version`; при конфликте клиент получает код 409 и выполняет повторную загрузку. REST: `POST /api/sessions`, `GET /api/sessions`, `GET /api/sessions/:id/full`, `POST /api/sessions/:id/patch`, `PUT /api/sessions/:id/state`. Доменная сущность Scene в проектной модели соответствует игровой сессии на уровне runtime-хранилища объектов стола.

#### 3.1.3 Клиентский редактор стола

`SessionTablePage` объединяет `CanvasRenderer`, `TableController`, `InspectorPanel`, иерархию объектов. `TableSync` буферизует патчи, debounce 300 мс, throttle 100 мс; передаёт cookie сессии при handshake Socket.IO. `HistoryManager` поддерживает локальный undo/redo до согласования с сервером.

#### 3.1.4 Модуль realtime

`registerRealtime` в `gateway.ts`: события `joinTable`, `table:patch`. Обработчик патчей вызывает `applyTablePatches` и рассылает `table:patchApplied`. При конфликте версий возвращается ack с ошибкой и статусом 409.

#### 3.1.5 Пакет @dnd-table/shared

Единый источник типов `TablePatchOp`, `AppliedOp`, схем компонентов. Сборка workspace обеспечивает согласованность контракта между клиентом и сервером.

#### 3.1.6 Инфраструктура

Переменные: `MONGODB_URI`, `SOCKET_CORS_ORIGIN`, `ASSETS_DIR`, `SESSION_SECRET`. Health-check `GET /health`. Скрипты: `npm run dev:backend`, `dev:frontend`, `npm test`, `npm run build`.

Архитектура модулей parties, scenes, ecs, users/friends, assets спроектирована в соответствии с доменной моделью раздела 2; их REST- и socket-контракты приведены в таблицах спецификации интерфейсов. Эксплуатационная синхронизация стола в развёрнутой версии системы реализована через gamesessions и realtime.

#### Обзор литературных источников по теме

В учебной и научной литературе вопросы проектирования информационных систем рассматриваются через призму жизненного цикла программного обеспечения. Для распределённых приложений с интерактивным UI актуальны модели клиент-серверного взаимодействия и обмена событиями в реальном времени. Методики объектно-ориентированного анализа (UML, RUP) применимы к декомпозиции VTT на подсистемы: учёт пользователей, управление партией, редактор сцены, синхронизация.

Публикации по качеству ПО (ISO/IEC 25010) задают рамки нефункциональных требований: производительность, надёжность, удобство использования. Документация промышленных технологий (Node.js, MongoDB, React, Socket.IO) используется как нормативно-техническая база при обосновании стека.

#### Детализация сущностей предметной области

Компонент **Transform** хранит вектор положения (x, y), опционально z-порядок, масштаб и угол поворота. **Shape** определяет тип геометрии (`rect`, `circle`) или ссылку на растровое изображение через `resourceId`. **Description** содержит текстовое поле для заметок ведущего или игроков. **Visibility** реализует fog-of-war и выборочную видимость: массив `visibleTo` может содержать идентификаторы пользователей или команд; флаг `hidden` скрывает объект от неавторизованных ролей. **Grid** задаёт шаг сетки для привязки перемещений.

Иерархия `parentId` позволяет группировать объекты (например, рамка карты и токены на ней). Поле `order` управляет z-order при отрисовке на Canvas.

#### 1.2.1 Roll20 (дополнительный анализ)

Платформа ориентирована на широкую аудиторию D&D и смежных систем. Экономическая модель подписки влияет на доступность продвинутых функций (динамическое освещение, API). С точки зрения проектирования ACL Roll20 не предоставляет декларативной матрицы действий на уровне отдельного объекта сцены — ограничения задаются преимущественно ролью листа и слоём карты. Для DnDTable это является мотивацией внедрения `PermissionResolver` с явными действиями.

#### 1.2.2 Foundry VTT (дополнительный анализ)

Foundry демонстрирует высокую гибкость за счёт модулей сообщества. Однако воспроизводимость конфигурации прав в разных инсталляциях низкая: набор модулей не стандартизирован. DnDTable проектируется с фиксированным ядром ACL в коде сервера, что упрощает тестирование и аудит безопасности.

#### 1.2.3 Owlbear Rodeo (дополнительный анализ)

Минимализм Owlbear снижает время входа в сессию, но переносит ответственность за долговременное хранение кампаний на внешние инструменты. DnDTable сохраняет партии и сцены в MongoDB, обеспечивая непрерывность кампаний.

#### 1.3.1 Детализация функциональных требований

Критический контур функциональности включает авторизацию, CRUD объектов стола, базовую синхронизацию и отображение на Canvas. Следующий уровень охватывает партии, инвайты и друзей. Расширенный уровень — ACL с оверрайдами, ассеты и иерархию teams.

Каждый REST-метод возвращает структурированные ошибки (`success`, `error`, `message`) через единый `errorHandler`. Socket-события при отказе в правах не применяют изменение и возвращают ack с кодом ошибки.

#### 1.3.2 Расчётные соображения по производительности

Требование 300 мс для типовой операции интерпретируется как 95-й перцентиль задержки на стенде: сервер Node на localhost, MongoDB без сетевой задержки, payload патча до 10 операций. При перетаскивании объекта клиент генерирует серию патчей; debounce 300 мс в `TableSync` агрегирует их в один запрос, снижая нагрузку на БД.

Масштаб «несколько тысяч пользователей» достигается на кластере с sticky sessions или Redis adapter для Socket.IO. Горизонтальное масштабирование MongoDB — sharding по `partyId` при росте объёма документов `scene_objects`.

#### 1.4.1 Сравнение методологий проектирования

Структурный подход (IDEF0, DFD) применим к описанию потоков данных между партией и сценой. Объектно-ориентированный подход (UML) — к классам `TableController`, `GameSessionsService`, моделям Mongoose. Для проекта выбран ОО-подход как соответствующий стеку TypeScript и модульной структуре репозитория.

#### 1.5.1 Обоснование MongoDB

Реляционная СУБД обеспечила бы жёсткие JOIN для иерархии объектов, но усложнила бы эволюцию схемы компонентов. Документная модель MongoDB позволяет хранить `components` как вложенный объект и индексировать по `sceneId` и `key`. Транзакции multi-document доступны при необходимости атомарного batch-update.

#### 1.5.2 Обоснование TypeScript и монорепозитория

Статическая типизация снижает класс ошибок при передаче `TablePatchOp` между клиентом и сервером. Workspaces объединяют `backend`, `frontend`, `packages/shared` в одной версии контракта.

### 2.2.1 Детализация вариантов использования UC-03

**Предусловия:** пользователь аутентифицирован, состоит в партии, имеет право `object.update` на объект или класс объектов.

**Основной поток:** (1) открыть сцену или игровую сессию; (2) выбрать инструмент; (3) создать или выделить объект; (4) изменить свойства в инспекторе; (5) клиент формирует патч; (6) сервер применяет и рассылает; (7) остальные клиенты обновляют Canvas.

**Альтернативный поток А1 (конфликт версий):** на шаге 6 сервер возвращает 409; клиент загружает полное состояние и повторяет операцию пользователя при необходимости.

### 2.3.1 Сценарии интерфейса для роли Player

Игрок видит ограниченный набор инструментов: перемещение разрешённых токенов, просмотр описаний, без доступа к ACL и удалению чужих объектов. Скрытые объекты (`Visibility.hidden` или `visibleTo` без id игрока) не отрисовываются.

### 2.3.2 Сценарии интерфейса для роли GM

Ведущий имеет полный доступ к иерархии, загрузке ассетов, настройке сетки, управлению слоями. Панель ACL доступна из контекста партии.

#### 3.1.1 Детализация реализации AuthService

Метод `register` выполняет нормализацию email (lowercase, trim), проверку коллизий, валидацию пароля `_isPasswordStrong`, хеширование bcrypt. Ответ содержит объект `user` без `passwordHash`. Метод `login` сравнивает хеш; при успехе устанавливается `req.session.userId`.

Маршрутизатор использует `express-validator` для синтаксических проверок и `validate` middleware перед вызовом сервиса. Ошибки домена — через `HttpError` с кодами `EMAIL_ALREADY_EXISTS`, `VALIDATION_ERROR`.

#### 3.1.4 Детализация CanvasRenderer и TableController

`CanvasRenderer` рисует сетку, объекты по слоям, рамку выделения, handles изменения размера. `TableController` обрабатывает pointer events: pan, zoom (с ограничением min/max scale), drag, resize, rotate. `pickHandle` определяет активный маркер трансформации.

`geometry.ts` реализует преобразования координат screen↔world, AABB для hit-test повёрнутых прямоугольников, попадание в область выделения.

#### 3.1.6 Детализация applyTablePatches

Алгоритм последовательно обрабатывает массив `ops`. Для `create` — вставка с `version=1`; уникальный индекс `(gameSessionId, key)` предотвращает дубликаты. Для `update` — атомарный `findOneAndUpdate` с условием по `version`; при неуспехе — запись в `conflicts`. Для `delete` — `deleteOne` с проверкой версии.

REST-дублирование: `POST /api/sessions/:id/patch` применяет те же функции и инициирует broadcast через `getIoInstance()`.

### 1.6 Жизненный цикл программного обеспечения и выбор процесса разработки

Применительно к DnDTable рассматриваемый аспект (1.6 блок 1) влияет на выбор архитектурных решений: централизация бизнес-правил на сервере, единый контракт `@dnd-table/shared`, разделение структурных операций ECS и высокочастотных патчей `table:patch`. Практика показывает, что игнорирование данного аспекта на этапе аналитики приводит к дорогостоящей переработке модулей realtime и хранения на этапе внедрения. ### 3.2.7 Реестр тест-кейсов

**TC-02 Вход с неверным паролем.** Шаги: открыть /login; ввести существующий email и неверный пароль; отправить. Ожидается 401, сообщение «Неверный логин или пароль». Важность: средняя. Воспроизводимость: всегда.

**TC-03 Доступ к API без сессии.** Шаги: выполнить GET /api/sessions без cookie. Ожидается 401 UNAUTHORIZED. Важность: высокая.

**TC-04 Создание игровой сессии.** Шаги: авторизоваться; POST /api/sessions с name; проверить GET /api/sessions. Ожидается новая запись. Важность: высокая.

**TC-05 Создание объекта на столе.** Шаги: открыть редактор сессии; инструмент rect; нарисовать область. Ожидается объект в иерархии и на Canvas. Важность: критическая.

**TC-06 Синхронизация между двумя клиентами.** Шаги: два браузера в одной сессии; клиент A перемещает токен. Ожидается совпадение координат у B в пределах 300 мс. Важность: критическая.

**TC-07 Конфликт версий.** Шаги: офлайн-правка объекта в двух клиентах; онлайн-отправка обоих патчей. Ожидается 409 у второго; reconcile. Важность: высокая.

**TC-08 Undo/redo.** Шаги: создать объект; Ctrl+Z; Ctrl+Y. Ожидается восстановление. Важность: низкая.

**TC-09 Health-check.** GET /health. Ожидается ok:true. Важность: низкая.

**TC-10 npm test.** Запуск из корня. Ожидается exit code 0. Важность: высокая.

### Развёртывание и эксплуатация

Установка: клонировать репозиторий; скопировать `infra/backend.env.example` в `backend/.env`; поднять MongoDB (`docker run` mongo:6); `npm install`; `npm run dev:backend` и `npm run dev:frontend`.

Production: `npm run build`; `npm start` для backend; статика frontend за reverse proxy (nginx). TLS терминация на proxy; cookie `secure: true`.

Резервное копирование: периодический `mongodump`; копирование каталога `ASSETS_DIR`.

Мониторинг: логи stdout сервера; метрики задержки патчей; алерт при недоступности /health.

### Историческая справка по VTT

Первые виртуальные столы появились как desktop-приложения с картой и токенами. Переход в браузер снизил барьер установки. Современные облачные сервисы монетизируют хостинг и маркетплейс ассетов. DnDTable занимает нишу открытого self-hosted веб-стека с акцентом на формальную модель прав — актуально для образовательных и корпоративных DM-групп.


#### 3.1.7 Детализация каталога backend/src/modules/auth

Модуль размещён в `backend/src/modules/auth`. Точка входа — `auth.router.ts`, бизнес-логика — `auth.service.ts`. Регистрация принимает email, username, password. Валидация express-validator проверяет формат почты, длину никнейма и минимальную длину пароля. Сервис проверяет уникальность email и username, применяет `_isPasswordStrong`, хеширует пароль bcrypt. При успехе в сессию записывается userId. Middleware `requireAuth` отклоняет запросы без авторизации кодом 401 JSON.

#### 3.1.8 Детализация каталога backend/src/modules/gamesessions

`GameSessionsService` инкапсулирует создание сессии, выборку списков, загрузку полного состояния и применение патчей. Модели `GameSession`, `TableObject`, `SessionState` описаны в Mongoose-схемах. Уникальный индекс по паре `(gameSessionId, key)` гарантирует идемпотентность создания объектов с клиентским ключом.

#### 3.1.9 Детализация каталога frontend/src/tabletop

Подсистема включает `geometry.ts`, `CanvasRenderer`, `TableController`, `TableSync`, `HistoryManager`. Vitest-тесты выполняются без поднятия DOM в headless-режиме. Hook `useTableSync` управляет жизненным циклом соединения и flush при `beforeunload`.

## ЗАКЛЮЧЕНИЕ

В ходе выполнения выпускной квалификационной работы разработана информационная система DnDTable — веб-ориентированный виртуальный стол для настольных ролевых игр. Поставленная цель достигнута: спроектирована и реализована архитектура, обеспечивающая совместную работу участников над игровым столом, хранение данных на сервере, синхронизацию изменений и проектирование разграничения прав.

В аналитической части описана предметная область, проведён сравнительный анализ аналогов Roll20, Foundry VTT и Owlbear Rodeo, сформулированы функциональные и нефункциональные требования. Обоснован выбор клиент-серверной архитектуры, MongoDB, Node.js/Express, React, Socket.IO и компонентной модели объектов. Зафиксированы принятые технологические решения: серверные сессии, Canvas 2D, протокол патчей с оптимистичной конкуренцией.

В проектной части разработана логическая модель базы данных, архитектура модулей монорепозитория, варианты использования и структура пользовательского интерфейса редактора. Текстовые описания диаграмм приведены в приложении Б.

В разделе реализации и тестирования описаны модули авторизации, игровых сессий, realtime-шлюза и клиентского редактора; проведены ручные и автоматизированные испытания. Критерии приёмки согласованы с результатами тестирования.

Перспективы развития связаны с эксплуатационным качеством: развёртывание кластера Node.js с Redis-адаптером Socket.IO для горизонтального масштабирования; подключение объектного хранилища S3/MinIO для ассетов; внедрение мониторинга (Prometheus/Grafana) и rate limiting на маршрутах авторизации; расширение набора интеграционных и нагрузочных тестов; периодический аудит безопасности веб-приложения.

## ПЕРЕЧЕНЬ ПРИНЯТЫХ ТЕРМИНОВ И СОКРАЩЕНИЙ

**ACL** (Access Control List) — список управления доступом; набор правил, определяющих разрешённые действия субъекта над ресурсом.

**API** (Application Programming Interface) — программный интерфейс приложения.

**ECS** (Entity–Component System) — подход к представлению объектов сцены как сущностей с набором компонентов.

**GM** (Game Master) — ведущий игры.

**REST** — архитектурный стиль взаимодействия компонентов через HTTP-методы.

**SPA** (Single Page Application) — одностраничное веб-приложение.

**TTRPG** (Tabletop Role-Playing Game) — настольная ролевая игра.

**VTT** (Virtual Tabletop) — виртуальный стол.

**WebSocket** — протокол полнодуплексной связи поверх TCP для обмена сообщениями в реальном времени.

## ПРИЛОЖЕНИЕ Б

### Б.1 ER-модель информационной базы (текстовое описание)

**Сущность User.** Атрибуты: `_id`, `email` (уникальный), `username` (уникальный), `passwordHash`, `avatar`, `createdAt`, `updatedAt`. Связи: один пользователь может состоять в многих партиях через `PartyMember`; может быть владельцем партий; может иметь дружеские связи.

**Сущность Party.** Атрибуты: `_id`, `name`, `description`, `ownerId` (FK → User), `settings` (объект). Связи: Party 1—* PartyMember; Party 1—* Scene; Party 1—* Team; Party 1—* Asset; Party 1—* AclRule.

**Сущность PartyMember.** Атрибуты: `partyId`, `userId`, `role` ∈ {GM, Player}, `teamId` (опционально). Уникальность пары (partyId, userId).

**Сущность PartyInvite.** Атрибуты: `partyId`, `email` или `invitedUserId`, `status` ∈ {pending, accepted, rejected}, `role`, `createdAt`.

**Сущность Team.** Атрибуты: `partyId`, `name`, `parentTeamId` (самоссылка для иерархии отрядов).

**Сущность Scene.** Атрибуты: `partyId`, `name`, `order`, `settings` (размер сетки, фон). Связи: Scene 1—* SceneObject.

**Сущность SceneObject.** Атрибуты: `sceneId`, `key` (строковый стабильный id клиента), `version`, `parentId`, `order`, `components` (вложенный документ Transform, Shape, Description, Visibility, Grid). Рекурсивная связь parentId → SceneObject.

**Сущность GameSession.** Атрибуты: `_id`, `name`, `createdBy`, `isPrivate`, `description`. Связи: GameSession 1—* TableObject; связь с SessionState для viewport.

**Сущность TableObject.** Атрибуты: `gameSessionId`, `key`, `version`, геометрия и визуальные поля, `components`. Уникальный индекс (gameSessionId, key).

**Сущность Asset.** Атрибуты: `partyId`, `sceneId?`, `storageKey`, `mimeType`, `size`, `uploadedBy`.

**Сущность AclRule.** Атрибуты: `partyId`, `subject` (user/team/role), `action`, `effect` (allow/deny), `resourceScope`.

Кардинальности: удаление Party каскадно логически удаляет или архивирует связанные Scene (политика приложения); физическое каскадное удаление в MongoDB настраивается на уровне сервиса.

### Б.2 Диаграмма вариантов использования (текстовое описание)

**Актор Guest.** Варианты: зарегистрироваться, войти в систему.

**Актор User (аутентифицированный).** Варианты: просмотреть dashboard, редактировать профиль, управлять списком друзей.

**Актор GM.** Включает возможности User. Дополнительно: создать/изменить/удалить партию; пригласить участников; создать сцену; настроить ACL; загрузить ассет; создать игровую сессию; полный CRUD объектов сцены.

**Актор Player.** Включает возможности User. Дополнительно: принять приглашение; открыть сцену или сессию; перемещать разрешённые токены; просматривать видимые объекты.

**Граница системы** охватывает веб-клиент и сервер DnDTable. Внешние системы: браузер, MongoDB, файловое хранилище.

**Связи include:** UC «Редактирование сцены» включает UC «Проверка ACL» и UC «Синхронизация realtime».

**Связи extend:** UC «Конфликт версий» расширяет UC «Применение патча» при несовпадении baseVersion.

### Б.3 Диаграмма компонентов (текстовое описание)

**Компонент React SPA.** Подкомпоненты: Router, страницы Auth/Dashboard/SessionTable, подсистема tabletop (CanvasRenderer, TableController, TableSync, HistoryManager), HTTP-клиент с credentials.

**Компонент Express API.** Подкомпоненты: auth.router, gamesessions.router, errorHandler, session middleware.

**Компонент Socket.IO Gateway.** Обработчики joinTable, table:patch; интеграция с applyTablePatches.

**Компонент Mongoose Models.** User, GameSession, TableObject, SessionState и проектные модели Party, Scene.

**Компонент @dnd-table/shared.** Zod-схемы, типы патчей.

**Компонент FileStorage.** Локальный ASSETS_DIR или адаптер S3 (перспектива эксплуатации).

Интерфейсы: REST JSON между SPA и Express; WebSocket между SPA и Gateway; драйвер MongoDB между Express и БД.

### Б.4 Диаграмма последовательности применения патча (текстовое описание)

**Участники:** ClientA, ClientB, SocketGateway, GameSessionsService, MongoDB.

1. ClientA: пользователь перетаскивает объект → TableController обновляет локальное состояние → TableSync формирует batch ops с baseVersion.
2. ClientA → SocketGateway: emit `table:patch` { tableId, ops }.
3. SocketGateway → GameSessionsService: applyTablePatches(sessionId, ops).
4. GameSessionsService → MongoDB: findOneAndUpdate с фильтром version.
5a. При успехе: MongoDB возвращает документ с version+1; Service формирует AppliedOp[].
5b. При конфликте: запись в conflicts; ack с 409.
6. SocketGateway → ClientA: ack { success, applied, conflicts }.
7. SocketGateway → room table:{id}: emit `table:patchApplied` { applied }.
8. ClientB: обработчик применяет AppliedOp к локальной модели → CanvasRenderer перерисовывает.

Альтернатива: ClientA отправляет POST /api/sessions/:id/patch без сокета; шаги 3–7 аналогичны; broadcast инициируется через getIoInstance().

### Б.5 Диаграмма развёртывания (текстовое описание)

**Узел ClientDevice.** Артефакт: статический bundle React (HTML, JS, CSS). Протокол HTTPS к reverse proxy.

**Узел AppServer.** Артефакт: процесс Node.js (dist/backend). Порты: HTTP 4000, WebSocket upgrade. Зависимости: переменные окружения MONGODB_URI, SESSION_SECRET.

**Узел DatabaseServer.** Артефакт: MongoDB 6 (standalone или replica set). Порт 27017.

**Узел FileStorage.** Каталог ASSETS_DIR на диске AppServer или отдельный MinIO/S3.

**Промышленная конфигурация:** Nginx (TLS, static, proxy_pass) → несколько экземпляров AppServer за балансировщиком; Redis для Socket.IO adapter; MongoDB replica set; отдельный volume для ассетов.

### Б.6 Макет редактора сцены (текстовое описание зон UI)

**Зона Header.** Название сцены/сессии, индикатор syncStatus, кнопки сохранения и выхода.

**Зона Hierarchy (слева).** Дерево объектов с drag-reorder; контекстное меню удаления; фильтр по слоям.

**Зона Canvas (центр).** Игровое поле с сеткой; pan/zoom; выделение; инструменты рисования.

**Зона Inspector (справа).** Поля Transform, Shape, Description, Visibility; привязка image resourceId.

**Зона Toolbar (низ или верх).** Инструменты select, rect, ellipse, text, image; undo/redo; масштаб.

Соответствие маршруту `/session/:sessionId` в развёрнутой версии клиента.
